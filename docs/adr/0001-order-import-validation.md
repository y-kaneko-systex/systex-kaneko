# ADR-0001: 受注 CSV の取り込みで、重複した商品行をどう扱うか

- Status: proposed
- Scope: 受注 CSV の取り込み（`import-orders`）で、同じ `external_key` が連続する1つのグループの中に、同じ商品コードの行が2行以上あるときの扱い。対象外：ほかの却下理由（`headerConflict`、`quantity`、`order.pack`、`noncontiguous` など）、行結果の保存形式、画面からの受注入力。
- Related As-Is documents: なし（`docs/as-is/` に As-Is 文書はまだない）。根拠にした採否表と観察は [findings/order-import.md](../as-is/findings/order-import.md) と [observations.md](../as-is/observations.md)。

## Context

人が決めること：同じ `external_key` のグループに同じ商品コードの行が2行以上あるとき、取り込みにどう振る舞わせるか。下の4案から1つを選ぶ。この草案は決定せず、案に順位も付けない。以下の事実は、コードとテストを読んで確かめたもので、実行して観察したものではない。

今の挙動：

- グループは、同じ `external_key` が連続する行のまとまり。検証 `validate()` は、グループの行を先頭から順に調べ、最初に見つけた1件で例外を投げて止まる。各行で、商品コードと数量以外の項目が先頭行と違えば `orderImport.headerConflict`、同じ商品コードが2回目に現れれば `orderImport.duplicateProduct`、数量が0以下なら `orderImport.quantity` の順に調べる。重複のメッセージは `Product occurs more than once: ` に商品コードだけを続ける。 [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/OrderCsv.java#L43-L54]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/OrderGroup.java#L66-L90]]
- 例外はグループ全体の却下になる。`importDraft()` は最初に `group.validate()` を呼ぶので、重複があれば受注の保存（`saveDraft`）に進まず、受注は作られない。 [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/OrderImportService.java#L34]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/OrderImportService.java#L64]]
- 却下は、グループ1つにつき `REJECTED` の結果1行として記録される。保存されるメッセージは、グループの範囲の説明（`external_key=…; source_rows=…; source_lines=…`）、`line <グループ先頭の行番号>: `、例外のメッセージの順。`line N` は重複した行ではなく、グループの先頭行の番号。`source_rows` はデータ行（見出し行を数えない）、`source_lines` はファイルの行番号。サンプルの CSV-ORDER-DUPLICATE（P001 が数量2と3の2行）から組み立てると `external_key=CSV-ORDER-DUPLICATE; source_rows=5..6; source_lines=6..7; line 6: Product occurs more than once: P001` になるはず（推測。実行して観察していない）。 [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/BatchOrchestrator.java#L136-L149]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/RowTask.java#L28-L31]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/RowTask.java#L60]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/OrderGroup.java#L121-L125]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/BatchRunService.java#L171]] [[source:samples/orders-rejections.csv#L6-L7]]
- 結果は、グループ番号をキーに1行。総数と却下数も、グループ1つにつき1ずつ加える。一部の行だけを却下したグループを表す項目は、結果の行（`BatchRow`）に見当たらない。却下が1件でもあると、取り込み全体は `PARTIAL`、終了コードは3になる。 [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/BatchRunService.java#L72-L90]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/BatchRunService.java#L163-L173]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/BatchRunService.java#L54-L55]]
- 1つの `external_key` に受注は1件（`external_key` と `order_id` が UNIQUE）。`canonicalHash()` は、商品と数量の行を並べ替えてからハッシュにする。同じ `external_key` で同じハッシュなら、新しい受注を作らず元の受注を返し（`orderImport.replayed`）、違えば `orderImport.keyConflict` になる（採否表 F-004、Decision は `pending`）。グループ内の行を並べ替えた CSV は再送として扱われ、数量を変えた CSV は終了コード3になる。 [[source:database/070-order-import.sql#L5-L7]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/OrderGroup.java#L92-L106]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/OrderImportService.java#L35-L37]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/service/OrderImportService.java#L84-L89]] [[source:wholesale-batch/src/test/java/jp/co/tsubame/wholesale/batch/OrderImportPostgresTest.java#L138-L147]]
- 受注を作るコア側にも、同じ商品の明細を2行置けない検査がある（`order.duplicateProduct`）。数量は 1〜1,000,000 で、商品の入数の倍数でなければならない。取り込みは数量を32ビット整数として読む。サンプルの P001 の入数は1、P004 は10。 [[source:wholesale-core/src/main/java/jp/co/tsubame/wholesale/service/OrderService.java#L121-L125]] [[source:wholesale-core/src/main/java/jp/co/tsubame/wholesale/common/Checks.java#L39-L43]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/ImportFields.java#L27-L34]] [[source:database/082-catalog-seed.sql#L17]] [[source:database/082-catalog-seed.sql#L20]]
- 採否表 F-003（Decision は `pending`）：同じ `external_key` が連続しない複数のグループに現れると、すべてのグループが `orderImport.noncontiguous` で却下される。この却下は、グループの検証より先に `reject()` で設定され、`validate()` が先頭で投げる。だから4案のどれを選んでも変わらない。この ADR が扱うのは、連続した1グループの中の重複だけ。 [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/BatchOrchestrator.java#L68-L80]] [[source:wholesale-batch/src/main/java/jp/co/tsubame/wholesale/batch/OrderGroup.java#L62-L67]]
- 特性テスト CHAR-ORD-001：`samples/orders-rejections.csv` の CSV-ORDER-DUPLICATE について、result が `REJECTED`、code が `orderImport.duplicateProduct`、作られた受注が0件、取り込み全体の終了コードが3、を固定している。メッセージの文言は固定していない。未コミットの変更で、実行していない（下の「確認できていないこと」）。 [[test:tests/characterization/order-import.characterization.test.mjs#CHAR-ORD-001]]
- ISSUE-001（`fixtures/issues/ISSUE-001.md`）は、この ADR が `accepted` になってから着手する Issue。範囲は、重複した商品の却下メッセージを ADR-0001 の決定どおりにする変更で、却下の単位を変えること（数量の合算、2行目以降だけの却下）は範囲外とされている。

確認できていないこと：

- OBS-001 が未記入。`docs/as-is/observations.md` の OBS-001 の行は、日時、環境、手順、観察した結果の欄がテンプレートの穴埋め記号のままで、実際の観察は入っていない。保存されるメッセージの実際の形を、観察で確かめていない。上の組み立てた文字列は、コードを読んだ推測。 (next read: ラボで `sh scripts/observe-import.sh samples/orders-rejections.csv` を実行し、CSV-ORDER-DUPLICATE の行の result、code、source_rows、message を OBS-001 に記録する)
- 採否表の F-003 は、重複した商品の規則ではなく、`noncontiguous` の規則。重複した商品の規則そのものを述べる行は、採否表にない（F-001〜F-006 はすべて `pending`）。ISSUE-001 は、重複の規則の出典を F-003 と OBS-001 としているが、この作業ツリーの採否表とは合わない。この ADR は、重複の規則を `OrderGroup.java` の該当行から直接引用した。 (next read: 人が、採否表に重複の規則の行を足すか、F-003 を見直すかを決める)
- CHAR-ORD-001 は、`git status` で未コミットの変更（`M`）になっている。この草案を作るときには実行していない（実行には Docker のラボが要る）。テストの内容は読んだが、緑であることは確かめていない。 (next read: ラボで `node --test "tests/characterization/**/*.test.mjs"` を実行する)
- 制約（期限、予算、技能、運用、コンプライアンス。ワークショップでは制約カード W3）は受け取っていない。比較には反映していない。 (next read: 制約カード W3)
- 取引先が同じ商品の行を重ねて送る理由（二重入力か、同じ商品の追加か）と頻度がわからない。案3・案4の妥当性に直結する。 (next read: 業務の担当者、取引先)
- 却下メッセージを誰が、どの経路で読むかがわからない（取引先に直接届くのか、運用の担当者が中継するのか）。運用や監視が文言を照合しているかも不明。リポジトリ内を検索した範囲では、`Product occurs more than once` の文言を読むコードは見つからなかった（含むのは `OrderGroup.java` と、Issue・テンプレートの文書だけ）。 (next read: 運用の担当者)
- 「メッセージだけでは、どの行を直せばよいかわからない」という困りごとが、実際にあるかがわからない。ISSUE-001 は「教材の想定」としていて、問い合わせや運用の記録は確認していない。 (next read: 問い合わせの記録、運用の担当者)
